## Decisions

1. **Translate at display time, not in the data.** `data/*.json` and the save keep the canonical English `name` (monsters, attacks) or `id` (classes, effects): monster art is looked up by English name, classes by id, and existing saves contain English attack names. Only the text put on screen is translated.
2. **Derived keys.** `LocalizedNames.key_for(prefix, name)` upper-cases the name and replaces every non-alphanumeric run with `_` (`"Giant Spider"` → `MONSTER_NAME_GIANT_SPIDER`). No extra `name_key` field is needed in the JSON, and the rule is one function that the test also uses. Monster attacks and player abilities share the `ABILITY_NAME_` prefix because they share names ("Strike").
3. **Safe fallback.** If a key is missing, the original data name is shown instead of a raw key; the test, not the player, catches the missing translation.
4. **Language change re-translates everything that is not rebuilt.** Runtime-built screens keep references to their static Labels/Buttons, which `_apply_menu_text()` updates. Dynamic texts (encounter header, fight log, attack list, class buttons, stat bars) are rebuilt when shown; `_select_locale()` also rebuilds the stat bars.
5. **How the test detects English.** `tests/verify_localization.gd` drives the real main scene through every view and modal (menu, settings, hub, exit confirmation, level up with class choices, exploration, treasure trap, every monster's encounter and fight-log line, monster attack list, abandon confirmation, retreat result) three times: English, launched in Spanish, and launched in English then switched to Spanish in Settings. For each visible Label/Button text and tooltip, a word found in the same node in English and Spanish that is not part of any Spanish translation is untranslated text; raw keys also fail. This catches hard-coded literals without keeping a list of English words. It also checks that both .po files have the same keys and that every data name has a translation.

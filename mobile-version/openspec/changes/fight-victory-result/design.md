## Decisions

1. **Own modal, not the game result modal.** `FightVictoryModal` is built with `_create_modal()` like the other dialogs and adds the underhand experience icon. Keeping it separate from `GameResultModal` means a victory is never mistaken for a run result (the playtest bot and the back handler tell them apart by node, not by title text), and the low-energy warning, which uses `GameResultModal`, can follow it without overwriting it.
2. **Replaces the experience overlay after a kill.** The victory result shows the same experience amount, so the 0.8 s flash would only repeat it. `_show_experience_overlay()` stays for other uses.
3. **Content.** "Enemy defeated: <name>" (neutral wording, so Spanish needs no article or gender for each monster), "+N dungeon experience" (omitted when N is 0) and "Dungeon experience this run: M. Retreat from the entrance or clear the dungeon to keep it." The last line ties into the energy-loss feedback (DNG-4): the experience is provisional. A fight gives no other reward today (no items or gold; reputation is granted on completion), so experience is the only reward line.
4. **Monster names.** Monsters have no id, so the key is derived from the data name: `MONSTER_NAME_` + upper-case name with spaces as underscores (`Giant Spider` -> `MONSTER_NAME_GIANT_SPIDER`). A missing key falls back to the data name. The key prefix avoids clashing with Godot's automatic translation of control texts, which an `msgid "Rat"` could trigger.
5. **Last monster: one result.** Killing the last monster completes the dungeon, which already shows the completion result and returns to the hub. Showing a victory result too would stack two dialogs, and its Continue ("back to the map") would make no sense once the run is over. The completion result therefore puts the victory lines (monster and experience, without the run total) above the completion rewards. `_complete_dungeon_if_ready()` takes an optional `victory_summary` for that.
6. **Last energy: depletion only.** A kill that spends the last energy while monsters remain ends the run, and the depletion result already explains what happened and the experience lost. No victory result is shown, as in the existing "victory resolves before depletion" order.
7. **Low-energy warning.** `_warn_if_energy_low()` still runs after the kill and still sets the once-per-run flag, but when the victory result is open it stores the message in `low_energy_warning_after_victory`. `_hide_fight_victory()` shows it after Continue. The player reads the result first, then the warning, never one over the other. If the app is closed while the victory result is open, the warning flag is already saved and the warning is not repeated; this is accepted as an edge case.
8. **Playtest bot.** The bot presses Continue on the victory result (calls `_hide_fight_victory()`) and keeps playing, the same way it dismisses the low-energy warning. A warning that follows is dismissed on the next step.
9. **Input cooldown.** The victory modal is in the input-cooldown watch list (change `input-cooldown-after-screen-change`), so the tap that won the fight cannot also press Continue.
10. **Delayed warnings respect the victory result.** A low-energy warning delayed by a damage overlay (`LOW_ENERGY_WARNING_DELAY_SECONDS`) can come due while a victory result is open. `_show_low_energy_warning()` then hands it to the victory result's Continue as well.
11. **Depleted exit finishes once.** `_finish_depleted_dungeon_exit()` now returns unless an exit is pending. The playtest bot settles the depletion notification right away, and the overlay's 0.8 s timer used to call the finish a second time and wipe whichever run was active by then. That made `verify_balance` depend on wall-clock timing (the same seed gave different rates, and once a "stuck" run). With the guard, repeated runs give identical numbers. In the real game the finish was already called once, so players see no difference.

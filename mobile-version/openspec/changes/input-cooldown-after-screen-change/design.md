## Decisions

1. **Duration:** 300 ms (`SCREEN_CHANGE_INPUT_COOLDOWN_MSEC`). A deliberate tap on a new screen needs the player to read it first, which takes longer than that. An accidental double tap lands within it: 300 ms is also the double-tap timeout Android itself uses.
2. **What starts it:** any visibility change of the screens (menu, hub, exploration, encounter, settings, level up), the modals (confirmation, result, fight victory, monster info) and the feedback overlay. Hiding counts too: closing the victory result reveals the map, and that tap must not fall through to a move arrow.
3. **Central hook:** `_watch_screen_changes_for_input_cooldown()` connects `visibility_changed` of all those nodes to `_start_input_cooldown()`. It covers every code path that switches screens, including future ones, without per-button changes. A new screen or modal only has to be added to `_screen_change_watched_nodes()`.
4. **How taps are dropped:** `_input()` on the root `Main` control calls `set_input_as_handled()` for `InputEventScreenTouch` and `InputEventMouseButton` while the cooldown is active. `_input` runs before GUI input, so no control receives the event. Both kinds are gated because Android delivers a touch as a screen-touch event plus an emulated mouse event. Press and release are both dropped, so no button is left half pressed. Key and drag events are not gated.
5. **Not gated:** direct method calls. The playtest bot and the tests drive the game by calling `_fight()`, `move_player()` and so on, which never go through `_input`.
6. **Test approach:** `tests/verify_input_cooldown.gd` pushes real `InputEventMouseButton` press and release events into the root viewport (`push_input` in viewport coordinates) at the centre of the real buttons. The headless display server does not route `Input.parse_input_event` touches to the window, so the mouse path is the one exercised end to end. Touch gating is checked through `_is_tap_event`.
